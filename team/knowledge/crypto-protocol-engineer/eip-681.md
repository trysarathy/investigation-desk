# EIP-681 payment requests (and Tron equivalents)

Source: ERC-681 "URL Format for Transaction Requests", status **Final**, requires ERC-20 and ERC-137,
`https://raw.githubusercontent.com/ethereum/ERCs/master/ERCS/erc-681.md` (canonical
https://eips.ethereum.org/EIPS/eip-681), accessed 2026-10-29 [VERIFIED].

## Syntax (verbatim ABNF)
```
request          = schema_prefix target_address [ "@" chain_id ] [ "/" function_name ] [ "?" parameters ]
schema_prefix    = "ethereum" ":" [ "pay-" ]
target_address   = ethereum_address
chain_id         = 1*DIGIT
ethereum_address = ( "0x" 40*HEXDIG ) / ENS_NAME
parameters       = parameter *( "&" parameter )
parameter        = key "=" value
key              = "value" / "gas" / "gasLimit" / "gasPrice" / TYPE
number           = [ "-" / "+" ] *DIGIT [ "." 1*DIGIT ] [ ( "e" / "E" ) [ 1*DIGIT ] ]
```
- `target_address` = the beneficiary for native payments, or **the contract** to call.
- `chain_id` is decimal (EIP-155). "If no `chain_id` is present, the client's current network setting
  remains effective": omitting it invites wrong-network payments.
- ERC-20 payment = call `transfer` on the token contract with `address` (beneficiary) and `uint256`
  (amount in **atomic units**). Spec example:
  `ethereum:0x89205a3a3b2a69de6dbf7f01ed13b2108b2c43e7/transfer?address=0x8e23ee67d1332ad560396262c48ffbb01f93d052&uint256=1`
- Scientific notation allowed and "strongly encouraged" for value (`2.014e18`), but "Only integer numbers
  are allowed, so the exponent MUST be greater or equal to the number of decimals after the point."
- "The indicated amount is only a suggestion … which the user is free to change." [all VERIFIED]

## Security considerations (verbatim points)
- "Changing either the recipient address or the amount transferred can be a profitable attack. Users
  should only use URLs received from authenticated sources with adequate integrity protection."
- Hex addresses take precedence over ENS; clients may reject ENS names visually similar to hex.
- For ERC-20, the wallet should display the amount in the token's units from `decimals()`, "possibly
  alerting the user to the uncertainty of the nominal unit." [VERIFIED]

## What Clearline generates (`src/lib/requests/present.ts eip681`) [VERIFIED in code]
```
ethereum:${tokenContract}@1/transfer?address=${receivingAddress}&uint256=${toBaseUnits(amount)}
```
e.g. 1,250.50 USDC → `ethereum:0xa0b8…eb48@1/transfer?address=0x…&uint256=1250500000`.
Correct per spec: target = token contract, `@1` = Ethereum mainnet, plain integer base units, 6 decimals
fixed by `USDC_DECIMALS` (correct for Ethereum USDC/USDT only).

Things to keep right when extending it:
1. **Always include `@chainId`** (`@1`, `@56`, `@8453`, `@42161`, `@10`, `@137`). Without it the payer's
   current network is used.
2. `uint256` must use **that contract's** decimals (BSC-USD = 18, see `erc20-trc20.md`); derive from the
   pinned official decimals, never a constant.
3. Never put an ENS name in `address=`.
4. The URI is integrity-sensitive: it is only as safe as the page serving it. The payment page shows the
   contract, network, address and amount in text beside the QR (it does today), because wallet support
   for ERC-20 EIP-681 is uneven and the amount is editable by the payer.
5. `pay-` prefix is optional; most wallets accept plain `ethereum:`. [ASSUMPTION: wallet behaviour varies;
   test with the wallets a pilot customer actually uses]

## Tron equivalents
There is no Tron standard equivalent to EIP-681 ratified as a TIP that this session could open
[could not verify; TIP index on github not searched exhaustively]. In practice Tron wallets accept a bare
base58 address in a QR, sometimes `tron:<address>?amount=…&token=<contract>` conventions that differ per
wallet [ASSUMPTION]. Clearline rule for Tron requests (not built: requests are Ethereum-only): QR = bare
address only; show token contract `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`, network "Tron (TRC-20)" and the
exact amount as text; never imply the wallet will pre-fill the amount or token.
