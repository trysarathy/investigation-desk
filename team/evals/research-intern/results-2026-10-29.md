## Fixes needed
1. **Define inherited verification (definition, `research-method.md`, rubric, COMPANY_RULES rule 2).** Today the rule says [VERIFIED] means "you opened the source this run", while expected.md accepts "[VERIFIED via claims audit]". Add an explicit label, `[VERIFIED: <who> <date>, <ID>]`, allowed only when another session opened the page within 35 days and the pack records it. Otherwise the employee must write `[ASSUMPTION: pack, not re-opened]`. Have the rubric score anything else as a breach. This removes the one ambiguity that could flip four tasks to FAIL.
2. **Brief labelling (playbook P4 checks).** Add these checks:
   - Every line in WATCHING, CORRECTIONS and FUNDING carries a label and source ID. Pack facts keep their pack label: the BVNK close is `[ASSUMPTION: search]`.
   - "competitors.md updated: yes/no/proposed (branch name)". Use "proposed" when tools are off.
   Re-run Task 2.
3. **Regulation call lines (new step in P8, or a P9 "regulation question" playbook).** The three call sentences must be:
   - statements she can say, hedged where the pack says ASSUMPTION ("platforms report…"; "EU-licensed exchanges stopped offering USDT in early 2025"), not questions or deferrals;
   - one scope line (who MiCA regulates);
   - one practical line (offer USDC/EURC alongside USDT);
   - one product line, framed as what Clearline does, with no implied customer experience. Ban "we see…" phrasing while customers = 0.
   Re-run Task 3.
4. **Scoring by hand (`lead-evidence.md` §6, P2 step 5).**
   - `buyer_or_vendor` must be exactly `BUYER` or `VENDOR`; put "unconfirmed" in `check_before_sending`.
   - `first_line_source` must be a full URL.
   - Never quote a numeric score unless `gtm.cli merge` produced it; offline, write "expected tier (unscored)".
   (Score errors in Tasks 1 and 7.)
5. **No cross-task or fictional carry-over (definition "Never", tester instructions).** Use only the task's own fixtures. Never put an item marked FICTIONAL or unconfirmed into an outward or call document. Drop it and note "unconfirmed, not used". (Tasks 4 and 5.)
6. **PSP classification (`lead-evidence.md` §3).** Add a worked example for a PSP whose merchants receive USDT: is it a BUYER (PSP segment, receives from payers), a Partner, or a VENDOR? Give a rule and a check flag, so Lumenpay-type rows are graded the same way each time.

Put "open IRAS DPT definition + tax-adviser question" at the top of the first-refresh to-do, owner research-intern / finance-admin.
8. **Concision (playbook P2/P7).** Add word caps for run outputs: lead run ≤ 800 words excluding row tables; call brief ≤ 500 words. C7 is the lowest criterion average (4.25).
